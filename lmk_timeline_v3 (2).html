Plain-language summary: lmkd only kills a process when two conditions are true at once: free swap has dropped below its 333MB safety margin, and the system is "thrashing" — pages that were just reclaimed are being faulted back in almost immediately, which shows up as a burst of swap-in + block-device I/O. Panel B below plots a related, measurable stand-in (swap-in + block-in, combined, from the vmstat summary). lmkd's own thrashing % is computed from page-cache refault/scan rates, so the two track each other but are not identical. Two I/O pulses (!1, !2) already happened before any app-level kill was logged; free swap most likely hadn't yet crossed the 333MB floor, so nothing was killed. The worst pulse (!3, 300MB/s combined) lines up almost exactly with the first kill of the cascade; the swap peak (!4, 735MB) lines up with the two highest-thrashing kills (eru/glassos_service, 300-301%).

Context added after later analysis: this capture was taken about 21.6 days after the tablet booted. A bugreport pulled on 10-09 found a kernel memory leak (kmalloc-64 slab, about 93 MB per day of uptime). It had grown unreclaimable kernel memory to about 2.5 GB (76% of RAM) when the tablet rebooted itself on 10-06 (hang_detect, uptime 25.5 days). The memory pressure shown below is most likely a symptom of that leak. At this capture the leak would have held roughly 2.3 GB, an extrapolated estimate, not a measurement. What allocates the objects, and whether it depends on this test configuration, is not yet known.
